# Паспорт проекта «ООП-прототип агента умного дома»

| Параметр | Значение |
| --- | --- |
| Название | ООП-прототип агента умного дома |
| Тип | Учебный прототип (объектно-ориентированное проектирование) |
| Статус | В разработке (итерация 1: модель данных и логика принятия решений) |
| Владелец | Учебный проект, 2026 г. |
| Стек | Python 3.11+, стандартная библиотека, CSV как формат обмена данными |

## 1. Проблема

Датчики умного дома (температура, освещённость, движение, дверь) генерируют
поток разнородных событий, но сами по себе они не принимают решений. Без
программного агента жильцу приходится вручную отслеживать показания и
реагировать на них: включать охлаждение при перегреве комнаты, проверять
открытую входную дверь, замечать движение в тёмном помещении в режиме
отсутствия. Ручной контроль медленный, легко пропускается и не масштабируется
на несколько комнат.

Дополнительная проблема — отсутствие единой модели предметной области:
пороги реакции, правила интерпретации событий и формат результата размазаны по
скриптам, из-за чего логику трудно проверить, расширить и объяснить.

## 2. Цель

Создать прототип агента умного дома на принципах ООП, который принимает поток
событий датчиков, применяет настраиваемые пороги реакции и формирует по каждой
комнате пару решений — по климату и по безопасности — в едином машиночитаемом
виде.

## 3. Задачи

1. Описать паспорт проекта: проблему, цель, задачи, продукт и ограничения.
2. Зафиксировать структуру репозитория (`docs/`, `data/`, `src/`, `tests/`) и
   правила работы с данными.
3. Подготовить синтетический набор сырых событий датчиков
   (`data/smart_home_events_raw.csv`) с колонками `time`, `room`,
   `temperature`, `light`, `motion`, `door`, `controller_mode`.
4. Реализовать словарь порогов реакции агента: климат (комфортный диапазон
   температур), свет (порог «темно»), безопасность (дверь, движение, режим
   контроллера).
5. Сформировать список событий датчиков в виде списка словарей.
6. Реализовать обработку событий циклом и правила принятия решений по климату
   (`keep_climate`, `turn_on_cooling`, `turn_on_heating`) и по безопасности
   (`security_ok`, `send_door_warning`, `send_intrusion_warning`).
7. Собрать решения в список и вывести их на экран в согласованном формате.
8. Инициализировать Git-репозиторий и зафиксировать первую итерацию коммитом.

## 4. Продукт

**Что получается на выходе итерации 1:**

- `docs/passport.md` — паспорт проекта (данный документ).
- `data/smart_home_events_raw.csv` — синтетический датасет сырых событий
  датчиков (6 записей, 4 комнаты, 3 режима контроллера).
- `agent_state.py` — исполняемый модуль агента: пороги реакции, список событий,
  функции принятия решений по климату и безопасности, сборка и печать
  результата.
- `src/` и `tests/` — зарезервированные каталоги для модулей и автотестов
  следующих итераций.

**Формат результата** — список словарей, по одному на событие:

```text
{'room': 'kitchen', 'climate_action': 'keep_climate', 'security_action': 'security_ok'}
{'room': 'hall', 'climate_action': 'keep_climate', 'security_action': 'send_door_warning'}
{'room': 'bedroom', 'climate_action': 'turn_on_cooling', 'security_action': 'security_ok'}
```

**Пользователь продукта** — жилец дома (получает понятные решения вместо
сырых показаний) и разработчик/студент (получает расширяемую модель с явными
порогами и правилами).

## 5. Ограничения

- **Данные синтетические.** Реальные устройства и протоколы (MQTT, Modbus,
  Home Assistant) не подключаются; CSV и список словарей имитируют поток
  событий.
- **Только чтение и решение.** Агент не управляет физическими устройствами:
  действия `turn_on_cooling`, `turn_on_heating`, `send_door_warning` —
  текстовые решения, а не команды исполнительным механизмам.
- **Один шаг обработки.** Нет накопления истории, сглаживания шумов,
  прогнозирования и обучения; каждое событие оценивается независимо.
- **Пороги статичны.** Заданы словарём в коде, без UI и без подстройки под
  жильца; изменение порогов требует правки кода.
- **Нет автоматизации тестов.** `tests/` пуст: проверка итерации 1 выполняется
  запуском модуля и сверкой вывода.
- **Нет сетевой части и БД.** Прототип запускается локально одной командой,
  без сервера, аутентификации и хранения состояния между запусками.
- **Ограничение по объёму.** Итерация 1 — учебный прототип, а не продукт,
  готовый к эксплуатации в реальном доме.

## 6. Структура репозитория

```text
smart_home_project/
├── agent_state.py          # агент: пороги, события, решения
├── data/
│   └── smart_home_events_raw.csv
├── docs/
│   └── passport.md
├── src/                    # модули следующих итераций (ООП-классы)
└── tests/                  # автотесты следующих итераций
```

## 7. Критерии готовности итерации 1

1. Все каталоги и файлы из раздела 4 существуют и закоммичены.
2. `agent_state.py` запускается без ошибок и печатает три строки решений,
   соответствующие событиям `kitchen`, `hall`, `bedroom`.
3. Решения по климату выводятся из порогов, а не захардкожены в результате:
   изменение температуры события меняет `climate_action`.
4. Паспорт содержит все пять обязательных разделов: проблема, цель, задачи,
   продукт, ограничения.
5. Репозиторий инициализирован, рабочее дерево чистое (`git status`).
